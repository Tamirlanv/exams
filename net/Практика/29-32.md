# Сетевое администрирование · практика 29–32

## Задание 29

В сети с некорректной выдачей адресов DHCP найдите ошибку в пуле, шлюзе или DNS-параметрах и исправьте её.

### Решение

**Среда:** Cisco Packet Tracer, маршрутизаторы 2911, коммутаторы 2960, PC-PT. Имена портов относятся к этим моделям. Для PC–SW и SW–R используйте Copper Straight-Through, для R–R/SW–SW — Copper Cross-Over или автоматический выбор. Дождитесь зелёных индикаторов. Команды show выполняются из привилегированного режима `#`; на запрос имени при сохранении нажмите Enter.

**Схема:** R1 Gi0/0 — SW1 Gi0/1; PC Fa0 — SW1 Fa0/1; Server-PT Fa0 — SW1 Fa0/2. Серверу задайте 192.168.10.53/24, шлюз .1; Services → DNS → On и запись A `server.lab.test` → 192.168.10.53.

**R1 — CLI:**

```cisco
enable
configure terminal
interface g0/0
 ip address 192.168.10.1 255.255.255.0
 no shutdown
 exit
ip dhcp excluded-address 192.168.10.1 192.168.10.99
ip dhcp pool LAN10
 network 192.168.10.0 255.255.255.0
 default-router 192.168.10.1
 dns-server 192.168.10.53
 exit
end
copy running-config startup-config
```
На PC выберите Desktop → IP Configuration → DHCP, затем выполните `ipconfig /all`, `ping 192.168.10.1`, `nslookup server.lab.test`. Если модель PC не поддерживает /all, посмотрите поля в IP Configuration.

**Проверка:** на R1 `show ip dhcp binding`, `show ip dhcp pool`. Адрес клиента из .100–.254, маска /24, шлюз .1, DNS .53. DNS-сервер находится вне выдаваемого диапазона. Если аренда отсутствует, проверьте порт, VLAN, интерфейс R1 и свободные адреса пула.
**Учебная неисправность:** в пуле LAN10 указаны default-router 192.168.10.254 и dns-server 192.168.10.99; таких служб по этим адресам нет. Сам клиент при этом может получить нормальный адрес.

Сопоставьте `ipconfig /all` клиента, `show running-config` и `show ip dhcp binding` маршрутизатора с планом адресации. Исправьте R1:

**R1 — CLI:**

```cisco
enable
configure terminal
ip dhcp pool LAN10
 no default-router
 no dns-server
 default-router 192.168.10.1
 dns-server 192.168.10.53
end
copy running-config startup-config
```
На клиенте `ipconfig /release`, `ipconfig /renew` либо переключите Static → DHCP в Packet Tracer. Повторите проверку параметров, ping шлюза и nslookup server.lab.test. Исправление пула само по себе не обязано немедленно обновить уже выданную аренду.

## Задание 30

В сети с проблемой разрешения имён проверьте DNS-настройки, найдите ошибочную запись и восстановите работу службы.

### Решение

**Среда:** Cisco Packet Tracer, маршрутизаторы 2911, коммутаторы 2960, PC-PT. Имена портов относятся к этим моделям. Для PC–SW и SW–R используйте Copper Straight-Through, для R–R/SW–SW — Copper Cross-Over или автоматический выбор. Дождитесь зелёных индикаторов. Команды show выполняются из привилегированного режима `#`; на запрос имени при сохранении нажмите Enter.

**Схема:** PC, DNS Server-PT и Web Server-PT подключены к SW1 Fa0/1, Fa0/2, Fa0/3 соответственно; маршрутизатор для одной подсети не нужен.

На PC откройте **Desktop → IP Configuration → Static**, введите:

| Узел | IPv4 | Маска | Шлюз |
|---|---|---|---|
| PC | 192.168.10.10 | 255.255.255.0 | не нужен |
| DNS | 192.168.10.53 | 255.255.255.0 | не нужен |
| WEB | 192.168.10.80 | 255.255.255.0 | не нужен |
На DNS в Services → DNS включите службу, создайте A-запись `www.lab.test` со значением 192.168.10.80 и нажмите Add. На WEB включите Services → HTTP. Клиенту в IP Configuration укажите DNS 192.168.10.53.

**Проверка:** `ping 192.168.10.53`, `nslookup www.lab.test`, `ping www.lab.test`; в браузере PC откройте `http://www.lab.test`. Ожидается ответ A=192.168.10.80 и страница сервера. Суффикс .test выбран для учебной зоны; внешний DNS такую частную запись не обслуживает.
**Учебная неисправность:** A-запись www.lab.test ошибочно указывает 192.168.10.81. Ping и HTTP к правильному 192.168.10.80 работают, а nslookup возвращает .81.

1. На PC сравните доступ по IP и результат `nslookup www.lab.test`.
2. На DNS в Services → DNS удалите ошибочную запись и добавьте A `www.lab.test` → 192.168.10.80.
3. Повторите nslookup и откройте сайт по имени. На реальном Windows при необходимости выполните `ipconfig /flushdns`; в симуляторе используйте повторный явный запрос к серверу и дождитесь обновления кэша.

**Результат:** возвращается .80 и открывается нужная страница. Если запрос не доходит до сервера вообще, сначала проверяют адрес DNS и доступность порта 53, а не содержимое записи.

## Задание 31

Настройте мониторинг состояния сетевого устройства или службы и определите признаки недоступности или сбоя.

### Решение

**Среда:** Ubuntu-монитор 192.168.10.10 и Linux-веб-сервер 192.168.10.80 в одной /24 через switch. На сервере установите `nginx`, запустите `sudo systemctl enable --now nginx`, разрешите TCP/80 от монитора. На мониторе установите curl.

Сохраните как `monitor.sh` и запустите `bash monitor.sh`:
```bash
#!/usr/bin/env bash
target=192.168.10.80
for attempt in {1..12}; do
  stamp=$(date -Is)
  if ping -c 1 -W 1 "$target" >/dev/null 2>&1; then host=UP; else host=DOWN; fi
  if curl --fail --silent --show-error --max-time 3 "http://$target/" >/dev/null 2>&1; then
    http=UP
  else
    http=DOWN
  fi
  printf '%s host=%s http=%s
' "$stamp" "$host" "$http" | tee -a monitor.log
  sleep 5
done
```
**Проверка сбоя:** в отдельной консоли учебного сервера выполните `sudo systemctl stop nginx`: ожидается host=UP, http=DOWN. Восстановите `sudo systemctl start nginx`, следующая проверка должна показать UP/UP. Если отключить виртуальный сетевой адаптер, обычно оба статуса DOWN. ICMP может фильтроваться, поэтому доступность службы оценивают отдельно. Для постоянного мониторинга задают порог нескольких ошибок подряд, уведомление и контроль восстановления.

## Задание 32

Проанализируйте журнал сетевых событий и выделите записи, указывающие на ошибку, отказ службы или подозрительную активность.

### Решение

**Среда:** Ubuntu-сервер SSH, журнал systemd; отдельный switch не обязателен. Схема: `клиенты → сеть → SSH-сервер → journal/syslog`. В условии конкретный журнал не дан, поэтому ниже используется учебный набор событий.

```text
10:00:00 kernel: enp0s3: Link is Down
10:00:05 systemd: nginx.service: Failed with result 'exit-code'
10:01:01 sshd: Failed password for invalid user admin from 192.168.10.50
10:01:03 sshd: Failed password for invalid user admin from 192.168.10.50
10:01:05 sshd: Failed password for invalid user admin from 192.168.10.50
10:02:00 sshd: Accepted publickey for operator from 192.168.10.10
```
Для реального сбора на учебной Ubuntu:
```bash
sudo journalctl --since '-30 min' -p warning --no-pager
sudo journalctl -u ssh --since '-30 min' --no-pager
sudo journalctl -u nginx --since '-30 min' --no-pager
ip -s link show enp0s3
sudo systemctl status nginx --no-pager
timedatectl status
```
**Анализ:** Link Down указывает на потерю физического/виртуального канала; Failed nginx — на отказ службы, его причину ищут в соседних записях. Повторные Failed password одного источника — возможный перебор или ошибочный клиент; требуется сверить контекст. Accepted publickey — успешный вход, легитимность подтверждают владельцем и расписанием. Сохраните журнал, проверьте NTP и не считайте последующее успешное событие доказательством связи с предыдущими ошибками без дополнительных данных.
