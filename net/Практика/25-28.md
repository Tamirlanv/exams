# Сетевое администрирование · практика 25–28

## Задание 25

В Wireshark захватите ICMP-трафик, определите IP-адреса отправителя и получателя и объясните последовательность обмена.

### Решение

**Среда:** две Windows VM/PC в изолированной LAN, Wireshark на A. **Схема:** `A 192.168.10.10/24 — switch — B 192.168.10.20/24`. Шлюз не требуется. На B в PowerShell администратора разрешите ICMP только от A:
```powershell
New-NetFirewallRule -DisplayName "Exam ICMP from A" -Direction Inbound -Protocol ICMPv4 -IcmpType 8 -RemoteAddress 192.168.10.10 -Action Allow
```

1. В Wireshark выберите интерфейс с 192.168.10.10, начните захват.
2. На A в терминале выполните `ping -n 4 192.168.10.20`.
3. Остановите захват и задайте display filter `icmp && ip.addr == 192.168.10.20`.
4. Откройте IPv4 и ICMP у пары пакетов. Request: источник .10, получатель .20, Type 8 Code 0. Reply: источник .20, получатель .10, Type 0 Code 0. Identifier и Sequence Number связывают запрос и ответ.
5. Сравните время пары для RTT и количество запросов/ответов. Сохраните pcapng.

**Ожидаемый результат:** 4 запроса и 4 ответа при отсутствии потерь. ARP перед первым ICMP — нормальное разрешение MAC, оно скрыто фильтром icmp. Если ответов нет, проверьте firewall B и выбранный интерфейс захвата; отсутствие ответа само по себе не определяет причину.

Справка: [Wireshark — фильтры отображения](https://www.wireshark.org/docs/man-pages/wireshark-filter).

## Задание 26

В Wireshark захватите DNS-трафик, определите запрос, ответ и используемые адреса/порты.

### Решение

**Среда:** Windows-клиент с Wireshark и Ubuntu DNS-сервер с установленным dnsmasq в изолированной LAN. **Схема:** `PC 192.168.10.10/24 — switch — DNS 192.168.10.53/24`. Серверу назначен статический IP, DNS-порт свободен на этом адресе.

На сервере установите пакет `sudo apt install dnsmasq`, создайте `/etc/dnsmasq.d/exam.conf`:
```ini
listen-address=192.168.10.53
bind-interfaces
no-resolv
host-record=www.lab.test,192.168.10.80
```
Выполните `sudo dnsmasq --test`, `sudo systemctl restart dnsmasq`; при активном UFW разрешите DNS:
```bash
sudo ufw allow from 192.168.10.0/24 to 192.168.10.53 port 53 proto udp
sudo ufw allow from 192.168.10.0/24 to 192.168.10.53 port 53 proto tcp
``` Это локальная зона без пересылки внешних запросов.

На PC запустите захват активного интерфейса, затем `nslookup www.lab.test 192.168.10.53`. Остановите захват и задайте фильтр `dns && ip.addr == 192.168.10.53`.

**Разбор:** запрос A идёт с .10:случайный_порт на .53:53; ответ — с .53:53 на тот же порт клиента. Сопоставьте Transaction ID, Query Name, тип A, Response flag и Answer 192.168.10.80. nslookup может дополнительно запрашивать PTR сервера и AAAA — выделите именно пару A. Крупные ответы могут использовать TCP; в этом стенде типично UDP. DNS over HTTPS здесь не применяется, поскольку запрос явно отправлен nslookup локальному DNS.

Справка: [Wireshark — фильтры отображения](https://www.wireshark.org/docs/man-pages/wireshark-filter).

## Задание 27

Используя ping, tracert и netstat, выполните диагностику заданной сетевой проблемы и сформулируйте вывод.

### Решение

**Среда:** Windows-клиент 192.168.10.10/24 → R1 192.168.10.1 → сервер 192.168.20.80/24; DNS 192.168.10.53 обслуживает `www.lab.test`. Все IP-маршруты заранее исправны. **Учебная проблема:** доступ по IP работает, по имени — нет.

В терминале клиента:
```bat
ipconfig /all
ping 127.0.0.1
ping 192.168.10.1
ping 192.168.20.80
tracert -d 192.168.20.80
nslookup www.lab.test
nslookup www.lab.test 192.168.10.53
netstat -ano
```
Сравните настроенный DNS с .53. Если явный запрос к .53 успешен, а обычный нет, исправьте DNS клиента. В PowerShell администратора, при имени интерфейса Ethernet:
```powershell
Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ServerAddresses 192.168.10.53
Clear-DnsClientCache
Test-NetConnection 192.168.20.80 -Port 80
```
**Проверка:** обычный nslookup возвращает .80, сайт по имени открывается. На сервере `netstat -ano` должен показывать LISTENING на 80; на клиенте при активном обмене возможно ESTABLISHED. **Вывод для заданного примера:** L3-связность работала, ошибочен адрес DNS. Это ожидаемые наблюдения учебного случая, а не результаты реально выполненного захвата. Звёздочки tracert могут быть фильтрацией ICMP, поэтому оценивайте их вместе с конечной доступностью.

## Задание 28

В топологии с ошибкой маршрутизации определите неправильный адрес или маршрут и восстановите связность.

### Решение

**Среда:** Cisco Packet Tracer, маршрутизаторы 2911, коммутаторы 2960, PC-PT. Имена портов относятся к этим моделям. Для PC–SW и SW–R используйте Copper Straight-Through, для R–R/SW–SW — Copper Cross-Over или автоматический выбор. Дождитесь зелёных индикаторов. Команды show выполняются из привилегированного режима `#`; на запрос имени при сохранении нажмите Enter.

**Оборудование:** 2 R, 2 SW, 2 PC.

**Подключение:**

```text
PC-A Fa0 — SW1 Fa0/1; SW1 Gi0/1 — R1 Gi0/0
R1 Gi0/1 (10.0.12.1/30) — R2 Gi0/1 (10.0.12.2/30)
R2 Gi0/0 — SW2 Gi0/1; SW2 Fa0/1 — PC-B Fa0
```

На PC откройте **Desktop → IP Configuration → Static**, введите:

| Узел | IPv4 | Маска | Шлюз |
|---|---|---|---|
| PC-A | 192.168.10.10 | 255.255.255.0 | 192.168.10.1 |
| PC-B | 192.168.20.10 | 255.255.255.0 | 192.168.20.1 |

**R1 — CLI:**

```cisco
enable
configure terminal
interface g0/0
 ip address 192.168.10.1 255.255.255.0
 no shutdown
 exit
interface g0/1
 ip address 10.0.12.1 255.255.255.252
 no shutdown
 exit
ip route 192.168.20.0 255.255.255.0 10.0.12.2
end
copy running-config startup-config
```

**R2 — CLI:**

```cisco
enable
configure terminal
interface g0/0
 ip address 192.168.20.1 255.255.255.0
 no shutdown
 exit
interface g0/1
 ip address 10.0.12.2 255.255.255.252
 no shutdown
 exit
ip route 192.168.10.0 255.255.255.0 10.0.12.1
end
copy running-config startup-config
```

**Учебная ошибка:** на R1 вместо маршрута к 192.168.20.0/24 настроен маршрут к 192.168.30.0/24. Чтобы воспроизвести ошибку на отдельной копии стенда, удалите правильную запись и добавьте неправильную сеть назначения с тем же next-hop 10.0.12.2.

**Диагностика:** `show ip route 192.168.20.10` не находит путь, хотя `ping 10.0.12.2` успешен. Сравните адрес PC-B, `show running-config` и таблицу маршрутизации. Исправьте R1:

**R1 — CLI:**

```cisco
enable
configure terminal
no ip route 192.168.30.0 255.255.255.0 10.0.12.2
ip route 192.168.20.0 255.255.255.0 10.0.12.2
end
copy running-config startup-config
```
**Проверка:** На PC-A в Desktop → Command Prompt выполните `ping 192.168.10.1`, затем `ping 192.168.20.10`; на PC-B — `ping 192.168.10.10`. На маршрутизаторах выполните `show ip interface brief` и `show ip route`. Ожидаются up/up и маршруты C/L к локальным сетям, S к удалённой. Первый ping может потерять пакет при ARP; повторите. Если ответов нет, проверьте шлюзы PC, маски, `no shutdown` и обратный маршрут. **Причина:** ошибочна сеть назначения статического маршрута, а не транзитный канал.
